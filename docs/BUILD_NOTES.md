## Диагностические логи сетевого пакета `[NETLOG]`

### Что это

Три файла, которые писались во время диагностики ошибки подключения к серверу
(клиент получал `ERR_PT_NETEXCP`, код 522):

| Файл | Что писало | Где создаётся |
|------|-----------|---------------|
| `wpacket_debug.log` | каждое поле, записанное в исходящий пакет (`WriteCmd`, `WriteChar`, `WriteShort`, `WriteLong`, `WriteSequence`, `WriteFloat`, `WritePktLen`) | `sources/Libraries/Server/sdk/src/Packet.cpp` |
| `sender_debug.log` | состояние `Sender` до и после `send()` | `sources/Libraries/Server/sdk/src/Sender.cpp` |
| `receiver_debug.log` | состояние при инициализации, перед/после `recv()`, проверки буфера | `sources/Libraries/Server/sdk/src/Receiver.cpp` |

Файлы открывались в **рабочем каталоге процесса** при загрузке, то есть появлялись рядом
с `Game.exe` в `Client\`. За одну сессию клиента `receiver_debug.log` разрастался примерно
до 3 МБ, остальные — до сотен килобайт. Код не отслеживается git, `.gitignore` содержит
`*.log`.

### Текущее состояние: выключено, код сохранён

Ни одна строка логирования не удалена — все закомментированы и помечены тегом `[NETLOG]`.
Конструкция `std::ofstream` убрана внутрь `#if`, который по умолчанию выключен, так что
файлы больше не создаются вовсе.

| Файл | Флаг | Значение | Помечено строк |
|------|------|----------|----------------|
| `Packet.cpp` | `DIAG_WPACKET_LOG` | `0` | 8 вызовов |
| `Sender.cpp` | `DIAG_SENDER_LOG` | `0` | 2 вызова |
| `Receiver.cpp` | `DIAG_RECEIVER_LOG` | `0` | 11 вызовов |

### Как вернуть обратно

Два действия в каждом из трёх файлов:

1. Поставить `1` в соответствующий `DIAG_*_LOG`.
2. Снять комментарий с нужных строк — они все начинаются с `// [NETLOG]`.

Полезно знать:

- Переименование флагов. Раньше назывались `DEBUG_WPACKET`, `DEBUG_SENDER`,
  `DEBUG_RECEIVER`; теперь `DIAG_*_LOG`. Причина — `DEBUG_LOG` в `Receiver.cpp` слишком
  общее имя, оно конфликтует по смыслу с игровым логированием.
- В `Packet.cpp` и `Sender.cpp` добавлен `#include <iostream>`. Без него ветка
  `#else` (`std::cerr`) не собирается — в исходном варианте заголовка не было.
- Конструкция потока выполняется на этапе статической инициализации, то есть файл
  создаётся при загрузке, даже если ни одна строка лога не сработает. Отсюда и
  предложение убирать именно её за `#if`, а не только вызовы.
- `WPACKET_LOG` стоит в горячем пути — по строке на каждое записанное поле. При
  включённом логе это заметная нагрузка.

### Проверка после включения

Логи должны появиться в рабочем каталоге запущенного процесса:

```
Client\wpacket_debug.log
Client\sender_debug.log
Client\receiver_debug.log      # для серверов — в их каталогах server\<имя>\
```

Не появились — значит `DIAG_*_LOG` остался в `0` либо сработал краш до первой записи.

## Переменные, влияющие на поведение

### `USE_DSOUND` — выбор звуковой подсистемы

`sources/Client/src/GameApp.h:3` — `#define USE_DSOUND`.

Признак определён: используется `DSoundManager` (DirectSound), а `CAudioThread` из
`AudioThread.cpp` не компилируется вовсе. При этом музыка всё равно выводится через
SDL_mixer — см. ветки `#ifdef USE_DSOUND` в `GameAppFrameMove.cpp`.

Две подсистемы сосуществуют, громкость пишется в обе, звук производит только вторая.
Это не ошибка, но при разборе звука легко сбиться.

### `WpeProtection` — часть протокола, а не диагностика

Каждый пакет клиент → сервер с командой из диапазонов `(0,500]` или `[6000,6500]` несёт
дополнительный 32-битный счётчик сразу после слова команды. `GateServer::ToClient::OnProcessData()`
проверяет его против счётчика сокета (`DataSocket::m_pktn`) и затем физически вырезает
4 байта из буфера приёма.

**Выключение на сервере сдвигает полезную нагрузку каждого пакета клиента на 4 байта.**
Три переключателя защиты — часть формата, а не необязательная диагностика.

### `CommEncrypt` и `RSAAES` — симметричная пара

Клиент и сервер должны совпадать. Проверялось в паре с `WpeProtection`.

## Особенности сборки

### Платформа

Только `Release|x86`. Серверные бинарники собираются под 32-битный Windows и запускаются
под Wine в Docker. Код, зависящий от разрядности указателя, здесь недопустим.

### `LIBDBC` — общая библиотека сетевого кода

`sources/Libraries/Server/sdk` линкуют **все пять** проектов: клиент и четыре сервера.
Поэтому изменение `Packet.h`, `Packet.cpp` или `Receiver.cpp` требует перелинковки всех
пяти, а не только одного сервера.

### Расположение выходных бинарников

Клиент собирается в `Client/system/Game.exe` и копируется отдельно. Серверные собираются
в `sources/Server/<имя>/Bin/`. Каталог `server/<имя>/*.exe` — под контролем git и содержит
бинарники из исходного импорта, а не результат локальной сборки.

### Кодировка исходников

Часть файлов до сих пор содержит не восстановленные комментарии с `U+FFFD`. Такие места
нельзя сопоставлять текстом снаружи — правки в них делаются побайтово, по номерам строк.
Обычный поиск и замена по содержимому в таких файлах не сработает.

Заголовки клиента могут быть без BOM при том, что содержат валидный UTF-8. Перед правкой
стоит проверять кодировку явно, а не полагаться на редактор.

### Запись в файлы

`debug_files`, `debug_python_project`, `*.log` — в `.gitignore`. Всё, что туда пишется,
в коммит не попадает.

## Таблицы клиента: что коммитится, а что нет

Каталог `Client/scripts/table/` содержит **41 `.txt` и 36 `.bin`**. Текстовые таблицы — часть
исходников, бинарные — скомпилированная форма тех же данных.

### Что нужно делать при правке таблицы

Правь `.txt`, потом запусти:

```
Client\compiler_table.bat
```

Скрипт вызывает `Game.exe table_bin` и пересобирает все `.bin` из `.txt`. Только после
этого клиент увидит изменения.

### `serverset.txt` — адреса Gate, куда подключается клиент

Файл **не** под контролем git: отцеплен через `git rm --cached` и перечислен
в `.gitignore`. В репозитории лежит исходная версия с адресами-заглушками, твоя локальная
копия — рабочая. Правь её свободно, изменения в `git status` не появятся.

Формат — TSV, одна строка на группу серверов:

```
//Number	Group Name	Affiliated Region          Gate Address 01..05
1	Local	Development	127.0.0.1	0	0	0	0
2	live	Development	97.98.97.97	0	0	0	0
```

| Колонка | Значение |
|---|---|
| `Number` | номер группы, начиная с 1 |
| `Group Name` | отображаемое имя группы |
| `Affiliated Region` | регион (`Development` и т.п.) |
| `Gate Address 01`…`05` | адреса Gate, до пяти штук |

Как это работает в коде:

- `GlobalVar.cpp` / `ServerSet.h` — класс `CServerSet` разбирает файл;
- `ServerSet.h:115-118` — читает до пяти адресов, **останавливается на первом значении
  `0`**. То есть ноль в колонке означает «дальше адресов нет», а не «адрес ноль»;
- `ServerSet.h:24` — `szGateIP[MAX_GROUP_GATE][16]`, максимум 5 адресов по 16 символов;
- `Client/scripts/table/ServerSet.bin` — та же таблица в бинарной форме, пересобирается
  автоматически.

Практический вывод: ставишь свой адрес Gate в первую колонку, остальные оставляешь `0`.
Пример локальной настройки:

```
1	Local	Development	192.168.1.73	0	0	0	0
```

Список зон отдельно: `Client/scripts/txt/server.tx` (и `server2/3/4.tx` — по умолчанию
`server.tx`). Выбор файла зависит от кодера в параметре запуска `/login:` (`Main.cpp:339-357`).

### Почему `.bin` отцеплены

Они генерируются из `.txt` и после каждой правки давали diff на сотни килобайт. Отцеплены
все 36 файлов, в `.gitignore` добавлено `Client/scripts/table/*.bin`.

Проверено, что у каждого `.bin` есть парный `.txt`, поэтому восстановить их можно в любой
момент: `Client\compiler_table.bat`.

### `.txt` остаются под контролем git

Отдельно отцеплены только `.bin` и `serverset.txt`. Остальные 40 текстовых таблиц
по-прежнему отслеживаются — в том числе `character_lvup.txt`, где лежит разметка уровней
до 150.

### Если хочешь вернуть что-то под контроль git

```
git add -f Client/scripts/table/<имя файла>
```

Принудительное добавление работает вопреки `.gitignore`. Убирать не нужно: эти таблицы
должны быть в репозитории.

## База данных игры `arbah_project`

В репозитории появился отдельный веб-проект `arbah_project/` — сайт со
справочником по игре: каталоги предметов (6337), монстров, существ и NPC,
таблица опыта и калькулятор боевых характеристик. Данные собираются из
игровых таблиц `server/GameServer/resource`, а не берутся со сторонних
сайтов, поэтому ID всегда совпадают с игрой.

Главная задача — быстро находить ID предметов и монстров для GM-команд:
у каждого предмета в каталоге есть готовая команда `make <id>,1`, которая
копируется по клику.

Разворачивается отдельным контейнером в общей сети `pko_default` рядом
с игровыми серверами:

```
docker compose -f docker-compose.arbah.yml up -d --build
```

**Полное описание проекта, функциональность и список доработок — в файле
`docs/ARBAH_PROJECT.md`.**

Этот проект не влияет на сборку серверов и клиента: отдельная папка,
отдельный контейнер, общих файлов с `sources/` нет.

## Триггеры на `character`: GroupServer делал DDL при каждом старте

### Симптом

После пересборки и перезапуска всех контейнеров не удавалось войти в игру.
`AccountServer`, `GroupServer` и `GateServer` поднимались, а **все четыре**
`GameServer` падали в самом начале инициализации:

```
[ODBC ERROR] State:40001, Native:1205,
Msg:[Microsoft][ODBC Driver 17 for SQL Server][SQL Server]Transaction
(Process ID 57) was deadlocked on lock resources with another process and
has been chosen as the deadlock victim. Rerun the transaction.
```

Цепочка fatal прямо в коде, ни одного повтора:

| Место | Что происходит |
|---|---|
| `db.h:20` | `DBOK(SQL_ERROR)` — ложь |
| `GameDB.cpp:178` | `CTableCha::Init()` возвращает `false` |
| `GameDB.cpp:3822` | `_tab_cha->Init() && ...` — `FALSE` |
| `GameApp.cpp:404` | `CGameApp::Init()` прерывается, сервер не стартует |

Падал запрос `select ... from character (nolock) where 1=2` — тот самый,
которым `CGameDB::Init()` проверяет схему таблицы.

### Что делают триггеры

`TR_I_Character ON character FOR INSERT` — при вставке персонажа берёт
поле внешности `olhe`, вытаскивает 5-й символ и пишет его в колонку
`icon`. То есть `icon` — денормализованная копия, чтобы интерфейсу и
рейтингу не разбирать `olhe` каждый раз.

`TR_D_Character_Friends ON character FOR DELETE` — при удалении персонажа
чистит записи в `friends` и уменьшает счётчик гильдии: `try_total`,
если удаляемый был главой (`guild_stat > 0`), иначе `member_total`.

Оба нужны: без них остаются сироты в `friends` и расходится число
участников гильдии.

### Где они создаются

Только в `sources/Server/GroupServer/src/DBConnect.cpp`, функция
`TBLAccounts::IsReady()`. Ни в одном `.sql`, ни в Lua, ни в Python
этих имён нет — GroupServer был единственным их создателем.

В `mssql/[1]GameDB.sql` слово «trigger» встречается дважды, и оба раза
про другое: колонка `mistrigger` (сериализованное состояние миссий,
рядом с `mission`, `misrecord`, `miscount`) и DEFAULT-ограничение
`DF_character_trigger`. Это данные, а не DDL-объекты.

### Почему это ломало запуск

`IsReady()` по названию должна **проверять** готовность — её и вызывают
с логом «begin check table [account]». Но вместо проверки она безусловно
выполняла `DROP TRIGGER` + `CREATE TRIGGER`, то есть DDL.

`CREATE`/`DROP TRIGGER` берёт на таблицу блокировку **Sch-M** (Schema
Modification). Запрос `where 1=2` данных не читает и берёт только **Sch-S**
(Schema Stability). Эти блокировки взаимно несовместимы — классический
дедлок.

`depends_on` в compose ждёт только **старта контейнера**, а не готовности
приложения, поэтому DDL GroupServer выполнялось одновременно с проверкой
схемы четырьмя GameServer. Раньше просто не совпадало по времени.

Надо отметить: диагностика вводила в заблуждение. В errorlog MSSQL
дедлоков не было, и первое время это выглядело как «дедлока не
происходило». На деле с SQL Server 2019 графы дедлоков не пишутся по
умолчанию — нужен флаг 1222, а он был выключен:

```
DBCC TRACESTATUS(1222) WITH NO_INFOMSGS;
```

Флаг включён глобально, но **не переживает рестарт контейнера**.

### Что изменено

`TBLAccounts::IsReady()` теперь создаёт триггер только если его нет:

```sql
IF OBJECT_ID('TR_I_Character','TR') IS NULL
    EXEC('CREATE TRIGGER ...')
```

Обычный перезапуск DDL не делает, Sch-M не берётся, гонки нет. Первое
создание базы по-прежнему отработает: до `IF OBJECT_ID` триггеров нет,
DDL выполнится — в этот момент GameServer ещё не запущены.

Изменение поведения одно: если поменять текст триггера в коде, на уже
созданной базе он сам не обновится. Лечится удалением триггера и
перезапуском GroupServer.

### Вторая правка: повтор при 40001

`sources/Libraries/Util/src/db.cpp`, оба варианта `cfl_rs::exec_sql_direct`.

`handle_err` переподключался только при кодах обрыва связи (`HYT00`,
`HYT01`, `01000`, `08S01`). Коды сериализации в списке не было, поэтому
дедлок считался фатальным. Добавлена проверка `40001` и `40501`: до трёх
повторов с паузой 200/400/600 мс, **без** переподключения — запрос ведь
не выполнялся, данные целы.

Нужна не только на старте: такие конфликты будут возникать и в игре, где
запросы идут постоянно.

### Про `READ_COMMITTED_SNAPSHOT`

Вариант «включить RCSI», который предлагался поначалу, здесь не помогает.
Он снимает блокировки «читатель против писателя», а у нас конфликт
«DDL против читателя схемы». Настройку применять не нужно.

### Проверка

После пересборки GroupServer и Util — запустить контейнеры и убедиться,
что в логах GameServer нет строк `[ODBC ERROR]`. Убедиться, что оба
триггера на месте и не отключены:

```sql
SELECT name, is_disabled FROM sys.triggers WHERE parent_id = OBJECT_ID('dbo.character');
```
