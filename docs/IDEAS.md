## 1. Громкость звуков: убрать провал в первых делениях ползунка

Статус: **диагноз подтверждён, правка готова.** Баг найден при разборе жалобы «звук
пропадает, если недокрутить ползунок, потом резко становится громко».

### Что сделать

Одна строка в `sources/Client/src/DSoundManager.cpp:145`:

```cpp
int DSoundManager::VolumeToDB(double theVolume)
{
	int aVol = (int) ((log10(1 + theVolume*9) - 1.0) * 2333);
	if (aVol < -2000)
		aVol = -2000;      // ← БЫЛО: -10000
	return aVol;
}
```

Значение уходит в `SetVolume` в сотых долях децибела. Сейчас всё тише −20 дБ уходит в
−100 дБ, то есть в абсолютную тишину; с правкой получает −20 дБ.

### Почему именно это

Порог `vol ≈ 0.043` в пересчёте на пиксели ползунка шириной 98 px (33 деления, шаг 3 px)
попадает ровно на первые два деления:

| пиксель | деление | master | дБ сейчас | дБ с правкой |
|---|---|---|---|---|
| 0 | — | 0.0000 | −10000 (тишина) | −2000 (амплитуда 0.100) |
| 3 | 1-е | 0.0306 | −10000 (тишина) | −2000 |
| 6 | 2-е | 0.0612 | −1888 (0.114) | −1888 |
| 9 | 3-е | 0.0918 | −1722 (0.138) | −1722 |

Три деления подряд уходят в тишину, четвёртое выскакивает сразу на ~11% амплитуды —
это и есть «меньше двух делений пропадает, потом резко громко». Выше порога кривая
равномерная: шаг между соседними делениями ≈ +3% амплитуды, разрывов нет.

### Побочный эффект

Ползунок перестанет быть выключателем: на нуле будет тихо, но слышно. Если нужно настоящее
отключение — добавить проверку в обработчик ползунка `_evtMainMusicMouseDown`
(`UISystemForm.cpp:957`): `if (fPos <= 0) SetVolume(0)`. Правильнее решать это там, а не
в функции перевода громкости.

### Смежное, не трогаем

Громкость эффектов применяется дважды: `SetSoundSize(fPos/10)` и
`mSoundManager->SetVolume(fPos/10)`, а в `DSoundInstance::RehupVolume` они
перемножаются — `VolumeToDB(mBaseVolume * mVolume * mMasterVolume)`. Практически не
мешает, потому что кривая выше порога ровная. Отдельная задача на будущее.

### Отдельно про ini

`Client/user/system.ini` в `[audio]` хранит `musicEffect` и `musicSound`, клиент
перезаписывает файл сам, и при `musicEffect=0` на старте звук выключен до первого
движения ползунком. Если это мешает — ставить в ini разумные значения (например 10)
или чинить сохранение настроек.

### Работа

Три минуты. Пересборка клиента `Release|x86`. Сервер не трогаем.

## 2. Отдельный рейт опыта для квестов

Статус: **отложено по решению владельца проекта.** Описывает идею и всё, что к ней
относится, чтобы вернуться к вопросу позже без повторного разбора кода.

### Идея

Сейчас квестовый опыт и обычный kill-опыт идут **разными путями**, и рейты на них
распрострастраняются по-разному. Хочется, чтобы квесты имели собственный множитель,
независимый от `Server.Rates.Global.EXP`.

По аналогии с уже существующим ключом это выглядело бы так:

```lua
Server.Rates.Global.MissionEXP = 1    -- Rate at which missions grant experience.
```

## Почему сейчас нельзя просто покрутить

Разберём, что происходит с опытом от убийства монстра:

```
CEventHandler::Event_ChaDie            EventCalculate.cpp:14 / :128
  → GetExp_New                          exp_and_level.lua:72
    → ShareTeamExp                      exp_and_level.lua:166
      → GetPlyExpRate                   exp_and_level.lua:247   ← глобальный рейт
        → ExpSystem                      functions.lua:6628
            → Server.Rates.Map[...]      functions.lua:6635-6636
            → Server.Rates.Day[...]      functions.lua:6638-6639
            → кап по Server.Level.Limit  functions.lua:6641-6642
```

Квестовый опыт идёт мимо всего этого:

```
ActionsProc                            MisSdk/MissionSdk.lua:3473-3479
    p1 = p1 * GetExpState(character) / 100    ← это НЕ рейт
  → AddExp                              CharScript.cpp:726-776
    → CFightAble::AddExpAndNotic        FightAble.cpp:2014
      → CFightAble::AddExp              FightAble.cpp:1979-2012
        → setAttr(ATTR_CEXP, …)
```

То есть квестовый опыт умножается **только** на `GetExpState` — это
`CCharacter::m_ExpScale` (`Character.h:713-714`), инициализируется 100 и меняется через
`CMD_PM_EXPSCALE` как штраф за лаг (`GameAppNet.cpp:753-848`). Живых ветвей там только
`100`: значения `50` и `0` закомментированы, так что множитель сейчас всегда равен 1.

Дополнительно: в квестовом пути **не проверяется потолок уровня**, поэтому большой квест
может «перепрыгнуть» уровень.

## Где именно вставлять

Одна точка — `MisSdk/MissionSdk.lua:3477`, ветка `AddExp` внутри `ActionsProc`:

```lua
actions[i].p1 = actions[i].p1 * GetExpState(character) / 100
actions[i].p2 = actions[i].p2 * GetExpState(character) / 100
```

Предлагаемая правка по смыслу:

```lua
actions[i].p1 = actions[i].p1 * GetExpState(character) / 100 * MISSION_EXP_RAID
actions[i].p2 = actions[i].p2 * GetExpState(character) / 100 * MISSION_EXP_RAID
```

с объявлением рядом с остальными рейтами в `variable.lua:30-36` и алиасом в том же стиле,
что уже есть на строках 532-539:

```lua
-- Server Rates
EXP_RAID = Server.Rates.Global.EXP
MF_RAID  = Server.Rates.Global.DROP
SetGlobalRates(MF_RAID,EXP_RAID)
TEAM_EXP_RAID = Server.Rates.Global.TeamEXP
ELF_EXP_GET_RAID = Server.Rates.Global.FairyEXP
SHIP_EXP_RAID = Server.Rates.Global.ShipEXP
Resource_RAID_ADJUST = Server.Rates.Global.Resource
```

## Что обязательно учесть при реализации

Ветку `AddExp` в `ActionsProc` покрывает **не все** способы выдачи квестового опыта.
Те же мимо-рейты идут:

| Функция | Файл:строка |
|---|---|
| `AddExpAndType` | `MissionSdk.lua:3533` → `CharScript.cpp:778` |
| `AddExpPer` | `functions.lua:5822` |
| `AddExpAll` | `functions.lua:5831` |
| `AddExp_1..6` | `functions.lua:6937-7077` |
| `QianAddExp` | `functions.lua:3585` |

Все они пишут `ATTR_CEXP` напрямую. Чтобы рейт работал везде, множитель надо провести
через каждую, а не только через `ActionsProc`. Обратная сторона: `ExpSystem` вызывается
**только** из `ShareTeamExp`, то есть только из kill-опыта, — поэтому «исправить» всё
через `ExpSystem` нельзя.

## Похожий случай, который уже есть

`Server.Rates.Global.MissionGold` объявлен в `variable.lua:35` с комментарием
«The rate that the player receives gold from missions» — но **нигде не читается**. Это
заготовка под ту же идею, сделанная в прошлом и не доведённая до конца. При реализации
стоит либо задействовать, либо удалить, чтобы не путать.

## Квестовые предметы — отдельная история

`GiveItem` (`MissionSdk.lua:3642` → `CharScript.cpp:1178`) кладёт предмет прямо в
инвентарь, без шансов и без рейтов. Если нужен и отдельный рейт для квестовых предметов,
точка та же — ветка `GiveItem` в `ActionsProc`.

При этом дроп предметов **для** квеста идёт через рейт: вторая ветка `Check_Baoliao`
в `FightAble.cpp:2226` использует `GetPlyDropRate`.

## Оценка сложности

Правка на одну функцию `ActionsProc` — около часа работы. Полное покрытие всех шести
способов выдачи — ближе к двум-трём часам, плюс тестирование на сервере. Конфиг при этом
остаётся в `variable.lua`, пересборка не нужна.

Самое простое, если устраивает потеря платёжного оборота. Тогда:

- заменить `HasIMP` / `TakeIMP` на операции с деньгами — вероятно `GetPlayer()` +

- пересчитать цены во всех `.lua` из `shop/`: сейчас они в единицах IMP, при переходе на

Оценка: основная работа — Lua и клиент, пересборка GameServer не нужна, клиент нужен.

### Вариант B: открыть магазин через NPC

Механика магазина не меняется, меняется только точка входа.

- В Lua добавить функцию открытия, вызываемую из диалога NPC — рядом с существующей

- в клиенте убрать/заблокировать вызов `CMD_CM_STORE_OPEN_ASK` (`PacketCmd_CS.cpp:941`),

Оценка: меньше, чем вариант A, если валюту оставляем IMP. Нужно найти механизм вызова
Lua из NPC-диалога — в проекте он есть, диалоги обрабатываются скриптами.

### Вариант A+B вместе

Не исключены: валюта — золото, точка входа — NPC. Тогда объём примерно складывается.

## 4. `AddExpAll` и `GetExp`: опыт выше 80-го уровня

Статус: **не сломано, но опасно. Починить перед использованием.**

### Главное: `AddExpAll` нигде не вызывается

`AddExpAll` (`functions.lua:5831`) объявлена, но **вызовов нет ни одного** — ни в квестах,
ни в `MissionSdk`, нигде. Это заготовка. Но она выглядит рабочей, и в этом опасность:
кто-нибудь напишет скрипт, вызовет её и получит либо ошибку, либо опыт в 50 раз меньше
ожидаемого.

Функцию **не удаляем** — она может пригодиться. Но перед применением требует починки.

### Три дефекта внутри

**(1) Захардкожен `80`, не связанный с `Server.Level.Limit`.**

```lua
if type == 1 then
    local exp_add = math.random(value1, value2)
    if lv < 80 then
        exp_new = exp_now + exp_add
    else
        exp_add = exp_add / 50          ← жёсткое 80, при потолке 150
```

**(2) Ветка `type == 2` не может выполниться в принципе.**

```lua
elseif type == 2 then
    local exp_up = CalExp[lv_next] - CalExp[lv]     ← CalExp не существует
```

`CalExp` ищется по всему `sources` и `server` — объявления нет, есть только три чтения
внутри этой же функции (`functions.lua:5825`, `5849`, `5855`). В Lua неинициализированная
глобальная переменная равна `nil`, а `nil` в арифметике роняет скрипт. То есть `type == 2`
не просто неверна — она гарантированно падает.

Заодно видно, что `AddExpPer` (`functions.lua:5822`) использует **тот же** несуществующий
`CalExp`, но `AddExpPer` **вызывается** — из `MissionSdk.lua:3418-3422` и
`MissionScript07.lua`. Значит этот путь работает только потому, что `GetExpState`
и `value` приходят такими, что ветка с `CalExp` не достигается, либо вызов идёт с
некорректными аргументами. Требует проверки на живой сервер.

**(3) В `type == 2` третья ветка выдаёт фиксированное число:**

```lua
else
    exp_new = exp_now + 10000       ← не зависит ни от уровня, ни от процента
```

### Зачем вообще было деление на 50

Это **не наказание за высокий уровень**, а защита от «переполнения опыта». Нашёл в
`QianAddExp` (`functions.lua:3585-3628`), где `/50` и `*50` встречаются парой:

```lua
if type == 2 then
    ExpGet = Num
    if lv >= 80 then
        ExpGet = math.floor(ExpGet / 50)     ← уменьшили
    end
end

exp = exp + ExpGet
if exp > nlexp then                            ← опыт перевалил за предел уровня
    exp = nlexp + math.floor((exp - nlexp) / 50)   ← излишек тоже поделили на 50
end
SetChaAttrI(Player, ATTR_CEXP, exp)

if lv >= 80 then
    ExpGet = ExpGet * 50        ← и обратно умножили для показа в уведомлении
end
```

Логика такая: после 80-го уровня опыт за уровень огромный, и без деления игрок
мгновенно перелетал бы потолок. Излишек сохраняется в `ATTR_CEXP`, но с уменьшенным
весом — фактически «хвост» опыта, который копится медленно. Уведомление показывает
полную величину (`* 50`), чтобы игрок видел реальное число.

Поэтому `/50` — это **часть механики**, а не баг. Убирать его целиком нельзя, иначе
вернётся мгновенное переполнение.

### Что делать

Заменить `80` на `Server.Level.Limit`, но сохранить саму механику деления. Схема:

```lua
local lv = GetChaAttr(role, ATTR_LV)
local limit = Server.Level.Limit
if lv < limit then
    exp_new = exp_now + exp_add
else
    exp_add = math.floor(exp_add / 50)      -- механику оставить!
    exp_new = exp_now + exp_add
end
```

Для `type == 2` нужно решить, что подставлять вместо `CalExp`. По смыслу подходит
`GetExp` — он уже есть в `functions.lua:6790-6790+`, заполнен ровно на 100 уровней
(`GetExp[1] = 0` … `GetExp[100] = 4176709541`). **Но `GetExp` кончается на 100-м,
а потолок теперь 150** — то есть при `lv >= 100` таблица вернёт `nil` и сложение снова
упадёт. Либо продлить `GetExp` до 150, либо использовать `DEXP` из `variable.lua`
(там ровно та же таблица опыта, что и в `character_lvup.txt`, и она уже на 150).

### Смежное: `FightAble.cpp` — работающий, в отличие от этого

`FightAble.cpp:1994,1998` содержит тот же захардкоженный `80` с делением опыта на 50,
и **этот код реально работает** — в отличие от `AddExpAll`. После перехода на 150 уровней
любой персонаж выше 80-го получает в 50 раз меньше опыта за бой. Это первоочередная задача,
нужна пересборка GameServer.

### Оценка

Lua-часть — минут пять, пересборка не нужна. `FightAble.cpp` — плюс пересборка GameServer.

## 5. Локализация клиента: подмена таблиц от другой сборки

Статус: **нужен ключ шифрования.**

### Что выяснено

Файлы `Client/scripts/table/*.bin` — не mystery-формат, а обычный DES-шифр с ключом
прямо в исходниках:

```
sources/Libraries/Util/src/LanguageRecord.cpp:5
__byte ENC_KEY[] = {0x42,0x34,0x19,0x56,0x10,0x14,0x29,0x72};
```

Алгоритм в `sources/Libraries/EncLib/src/enclib.cpp`: к строке приклеиваются 4 случайных
байта, ими XOR-ится остаток, дальше DES ECB и кодирование в hex, по одному блоку на строку.

Проверено на текущем `StringSet.bin`: **расхождений с `StringSet.txt` — 0 из 959 строк.**
То есть `.bin` содержит ровно тот же текст, только зашифрованный.

Реализация шифра на Python лежит в `debug_python_project/stringset_crypt.py`
(папка в `.gitignore`), DES портирован из `sources/Libraries/EncLib/src/d3des.cpp`
в `debug_python_project/d3des_port.py` — со сверкой по эталонному тестовому вектору.
Команды: `dec` расшифровывает `.bin` в `.txt`, `enc` собирает обратно.

### Важно: как вообще делается локализация

Клиент читает `StringSet.bin`, а если его нет — `StringSet.txt`. Генерация бинарника
происходит **только если файла ещё нет**:

```cpp
// LanguageRecord.cpp:97-98
if(-1 != access(szBinFile, 0))
    return false;      // .bin существует — ничего не делаем
```

Поэтому рабочий способ — **подменить `StringSet.txt`, удалить `StringSet.bin`,
запустить клиент** (он соберёт бинарник сам) или прогнать `Client/compiler_table.bat`.
Подмена чужого `.bin` тоже сработает, но файл станет нечитаемым для правки.

### Проблема с бинарниками 1.38

В `debug_files/binary_table/` лежат 33 бинарника от старого клиента, включая
`StringSet.bin` (214 094 байта, 1999 строк против 958 в текущем).

Формат **совпадает**: те же hex-строки, те же длины в первых строках (48, 112, 48, 64…),
та же DES-статистика (≈50% байт ≥ 0x80). Но расшифровать текущим ключом не получается —
значит, **в той сборке другой `ENC_KEY`**. В истории репозитория ключ всегда был один
и тот же, так что подобрать его из кода нельзя.

### Что нужно, чтобы продолжить

1. **Ключ из `ENC_KEY` той сборки** — 8 байт. Если есть исходники или `Game.exe` старого
   клиента, можно поискать константу в бинарнике.
2. Либо — проверить, не используется ли там другой `LanguageRecord.cpp` с иным ключом.

После расшифровки `StringSet.txt` из 1.38 можно будет выборочно перенести нужные строки
в текущий файл, а не подменять бинарник целиком. Это безопаснее: индексы привязаны
к вызовам `GetString(N)` в C++, и в старой сборке нумерация может отличаться.

### Мелочь, найденная попутно

Нумерация индексов в `StringSet.txt` имеет пропуск: **отсутствует `[805]`**, строки идут
`[804]` → `[806]`. В коде на `GetString(805)` никто не ссылается, так что это безобидно.
Но при переносе строк из 1.38 индексы сверять надо руками: они привязаны к коду,
а не к порядку строк в файле.

Ещё две строки файла — `440` и `910` — остались в **GBK**, а не в UTF-8:

```
440:  "npc.clu界面<%s>上找不到控件<%s>"
910:  "%d个"
```

Остальные 956 строк — чистый ASCII. При правках кодировку этих двух надо учитывать.

### РЕШЕНО: ключ найден, файлы расшифрованы

Ключ от старой сборки нашёлся в `debug_files/any_files/Game.exe` (смещение `0x307520`):

```

```

Для сравнения, ключ текущей сборки (`LanguageRecord.cpp:5`):

```

```

Оба клиента используют один и тот же алгоритм, различается только ключ.

Расшифровано 33 бинарника из `debug_files/binary_table/`. Команда:

```
python debug_python_project\stringset_crypt.py dec <файл.bin> <out.txt> --138
```

Флаг `--138` выбирает ключ старой сборки, без него используется текущий.

#### Что в локализации 1.38

| Показатель | Значение |
|---|---|
| строк в `StringSet` 1.38 | 1998 (индексы до 2999) |
| строк в текущем клиенте | 958 |
| общих индексов | 958 |
| только в 1.38 | 1040 |
| только в текущем | **0** |
| текст совпадает дословно | 927 из 958 (**96,8 %**) |

То есть текущая версия — это **вырезка** из 1.38, ничего не добавлено. Из 31 различия
большинство безобидны (`Hunt ` → `Hunt`, `Socket 1: ` → `Socket 1`), но есть содержательные:

```
[177]  1.38: https://tortuga.talesofpirates.org/forgot
       текущий: PAI: The account does not exist. Please re-enter.

```

Строка `[177]` в 1.38 указывала на сайт, `[715]` использовала символ доллара вместо `G`.

#### Китайская локализация есть, индексы 1003..1998

В файле 1.38 найдено 735 строк с не-ASCII, из них 123 содержат китайские иероглифы,
все — в диапазоне индексов **1003..1998**. Английская часть — индексы 0..999
(с 165 строками GBK-остатков), китайская — 1000 и выше.

**Важно:** читать эти строки нужно **как GBK, а не как UTF-8**. При декодировании в UTF-8
получается мусор (`锟斤拷` вместо иероглифов). Текст надо читать в байтах и декодировать GBK:

```python
body = raw_bytes.decode("gbk")
```

Тот же эффект даёт `锟斤拷` — классический признак двойной перекодировки.

Клиент читает `StringSet` как ANSI/GBK, поэтому китайский текст переносится в `.txt`
только если сам файл остаётся в исходной кодировке, а не переписывается в UTF-8.

#### Как перенести

Подмена целиком не нужна и даже рискованна. Лучший путь: взять текущий `StringSet.txt`
и точечно заменить нужные строки. Скрипты для сравнения:

```
python debug_python_project\compare_locales.py      ← различия между сборками
python debug_python_project\check_138_bytes.py     ← поиск китайских строк
```

Индексы свереять руками: они привязаны к вызовам `GetString(N)` в C++.

## 6. Переполнение опыта в 32 битах: потолок выше 100 невозможен

Статус: **критично. Таблицы до 150 уровня нерабочие начиная с 101-го.**

### Где обрезается

Опыт хранится в 32-битных полях на **всех** уровнях — сервер, клиент и база:

```cpp
// sources/Libraries/common/include/LevelRecord.h
class CLevelRecord {
    long        lID;
    short       sLevel;
    unsigned int ulExp;        // ← 32 бита
};

// sources/Libraries/common/src/LevelRecord.cpp:28
pInfo->ulExp = _atoi64(ParamList[m++].c_str());   // ← парсится в 64 бита...
                                                   //   ...и обрезается до 32

// FightAble.cpp:1854 и 1985
unsigned int lCurExp = (unsigned int)m_CChaAttr.GetAttr(ATTR_CEXP);

// GameDB.cpp:539 — запись в базу
DWORD exp = (long)pCha->getAttr(ATTR_CEXP);

// UIStartForm.cpp:1241 — вывод в интерфейс
void CStartMgr::RefreshMainExperience(long num, long curlev, long nextlev)
```

`_atoi64` вернул полное число, но при присвоении в `unsigned int` остаются младшие 32 бита —
значение делится на `2^32` по модулю.

### Масштаб

Максимум `unsigned int` — `4 294 967 295`. Накопленный опыт на 150-м уровне из нашей таблицы:

```
2 837 244 395 562   ← в 1321 раз больше, чем влезает в 32 бита
```

| уровень | в таблице | после обрезки mod 2³² |
|---|---|---|
| 100 | 4 176 709 541 | 4 176 709 541 — ещё помещается |
| 101 | 4 468 969 644 | **174 002 348** |
| 102 | 4 807 406 843 | 512 439 547 |
| 140 | 656 141 872 775 | 3 306 843 783 |
| 149 | 2 450 442 189 611 | 2 310 830 891 |
| 150 | 2 837 244 395 562 | 2 565 980 202 |

**50 уровней из 150** содержат значения, которые сервер прочитает как мусор.
Первый такой — **101-й**.

### Что произойдёт в игре

Сервер проверяет левелап так:

```cpp
// FightAble.cpp:1867
if (lCurExp >= pCLvRec->ulExp)
```

После обрезки `ulExp` на уровнях 101+ становится **маленьким** (например, 174 миллиона
вместо 4,4 миллиарда). Значит условие левелапа выполнится немедленно, и персонаж
начнёт бесконечно повышаться, застревая на первом же переходе. Плюс рассинхрон с клиентом:
клиент читает ту же обрезанную таблицу, но интерфейс покажет «опыт: 2 565 980 202»
при потребности в 2,8 триллионе.

### Жёсткий предел

При 32-битном хранении максимально достижимый накопленный опыт — `4 294 967 295`.
Последний безопасный уровень по нашей таблице — **100** (опыт 4 176 709 541).

Это не совпадение: оригинальные авторы и так сделали потолок 100. Именно поэтому
`GetExp[]` в `functions.lua:6790` заполнена **ровно на 100 уровней** — не баг,
а следствие ограничения. Мы это увидели только сейчас, когда потолок подняли до 150.

### Варианты решения

**A. Вернуть потолок 100.** Самое честное: при 32-битном хранении выше 100 уровня
не получится физически. Ничего не ломается, `GetExp` работает как задумано.
Но тогда и `DEXP`, и `character_lvup` надо урезать до 100.

**B. Пересчитать таблицу так, чтобы всё влезало в 32 бита.** Можно, если строить её
от максимума вниз, а не от минимума вверх. Тогда на 150-м уровне будет ~4,2 миллиарда,
и каждый шаг будет небольшим. Реально — таблица переворачивается: сейчас она растёт
геометрически с коэффициентом ~1,158, и до 150 доходит до триллионов. Нужно другое
распределение, например линейное от 100-го уровня. Тогда 150 уровней достижимы.
Но проверка левелапа полностью переписывается, и это надо тестировать.

**C. Сменить тип на 64 бита.** `unsigned long long` в `CLevelRecord`, `DWORD` → 64-бит
в `GameDB`, `long` → 64-бит в UI, плюс формат пакета `WRITE_LONG` → другой тип.
Это правка потолка во всей игре и пересборка клиента с сервером. Самое правильное,
но самое дорогое.

### Смежное

`GetExp[]` в `functions.lua` кончается на 100 — при потолке 150 обращение к `GetExp[101]`
даёт `nil`, и арифметика падает. Это отдельный дефект, независимо от переполнения,
и чинить его нужно в любом случае (заменить на `DEXP` из `variable.lua`, где уже 150).

### Оценка

Вариант A — час работы. Вариант B — несколько часов расчётов и тестов. Вариант C —
правки в нескольких файлах, пересборка клиента и всех серверов, проверка базы.

Проверка выполнена только по коду, на живом сервере не воспроизводилось.
Скрипты: `debug_python_project/check_exp_overflow.py`, `check_exp_overflow2.py`.

### Вариант C подробно: `unsigned long long` вместо 32 бит

Самый правильный путь, если проект долгоживущий. Суть: убрать искусственный потолок
в 100 уровней и хранить опыт в настоящих 64 битах.

#### Где сейчас 32 бита — полный список

| Место | Строка | Код |
|---|---|---|
| `LevelRecord.h` | класс `CLevelRecord` | `unsigned int ulExp;` |
| `LevelRecord.cpp` | 28 | `pInfo->ulExp = _atoi64(...)` |
| `FightAble.cpp` | 1854 | `unsigned int lCurExp = GetAttr(ATTR_CEXP)` |
| `FightAble.cpp` | 1985 | `uLong lCurExp = GetAttr(ATTR_CEXP)` |
| `FightAble.cpp` | 2000 | `GetLevelRecordInfo(80)->ulExp` |
| `GameDB.cpp` | 539 | `DWORD exp = (long)pCha->getAttr(ATTR_CEXP)` |
| `GameDB.cpp` | 306 | чтение из базы `_atoi64(...)` |
| `UIStartForm.cpp` | 1241 | `RefreshMainExperience(long num, ...)` |
| `ChaAttr.h` | 25 | `LONG32 GetAttr(long lNo)` — сам атрибут |

Обратите внимание на `LONG32 GetAttr` в `ChaAttr.h` — **это отдельное ограничение**.
Атрибут опыта лежит в общем массиве `LONG32 g_lMaxChaAttr[ATTR_MAX_NUM]`, то есть даже
если расширить `CLevelRecord`, атрибут всё равно обрежется при записи. Менять придётся
либо сам атрибут, либо добавлять отдельное 64-битное поле для опыта.

#### Что надо поменять

1. **`CLevelRecord::ulExp`** → `unsigned long long` (или `uint64_t`).
   Учесть: `_ReadRawDataInfo` читает `_atoi64`, парсинг менять не нужно.

2. **Атрибут опыта.** Либо расширить `LONG32` → 64 бита для `ATTR_CEXP`, `ATTR_CLEXP`,
   `ATTR_NLEXP`, либо ввести отдельный `uint64 lExp64` в `CChaAttr`. Второе чище:
   общий массив атрибутов трогать не нужно, а перенос делается в одном месте.

3. **`FightAble.cpp`**: `unsigned int lCurExp` → 64 бита в обеих функциях
   (строки 1854 и 1985). Там же убрать магию `/50` или оставить, но пересчитать.

4. **`GameDB.cpp`**: `DWORD exp` → 64 бита при записи, `_atoi64` при чтении уже есть.
   Проверить тип колонки в базе — если она `INT`, потребуется `BIGINT` и миграция.

5. **Пакет клиент-сервер.** `ATTR_CEXP` передаётся в `NetSins`/`HMs` пакетах.
   Надо найти структуру атрибутов и расширить поле, иначе клиент получит обрезанное
   значение и покажет неправильный прогресс-бар.

6. **Клиент**: `UIStartForm.cpp:1241` принимает `long` — нужен 64-битный тип
   и пересчёт в `RefreshMainExperience`. Полоса опыта в интерфейсе.

7. **Lua**: `_atoi64` в Lua-слое, скорее всего, уже 64-битный (через `long long`),
   но надо проверить `SetChaAttrI` — если он тоже обрезает до 32 бит, дефект останется.

#### Порядок работы

Правильнее менять **от хранения к выводу**: сначала `CLevelRecord` и атрибут,
затем серверные вычисления, потом пакет и клиент. Если начать с интерфейса,
придётся дважды проходить по всем местам.

#### Сложность

Это правки минимум в 6 файлах плюс схема базы. Пересборка клиента и всех пяти серверов.
Оценка — полдня работы плюс тесты на живом сервере: нужно проверить, что персонаж
доходит до 150 и выше, а прогресс-бар не врёт.

#### Что это даёт

Потолок перестаёт быть искусственным. Таблица `character_lvup.txt` снова может
расти геометрически (текущая геометрия ×1,158 на 150-м даёт 2,8 триллиона — это
в 1321 раз больше теп��ршнего, но в 64 битах помещается с запасом).
Плюс исчезает необходимость в `/50` как в костыле и ограничение в 100 уровней.

### Дополнение: остальные таблицы 1.38 расшифровать не удалось

`StringSet` расшифрован — там DES с найденным ключом. А остальные 32 таблицы
(`iteminfo`, `characterinfo`, `skillinfo`, `monsterinfo` и прочие) используют
**другой шифр**: AES-128-GCM, ключ и IV лежат в
`sources/Libraries/common/src/TableData.cpp:6-7`:

```cpp
const unsigned char cluTableKey[] = { 0x32,0x72,0x35,0x75,0x38,0x78,0x2f,0x41,
                                      0x3f,0x44,0x28,0x47,0x2b,0x4b,0x62,0x50 };
const unsigned char cluTableIV[]  = { 0x43,0x2a,0x46,0x29,0x4a,0x40,0x4e,0x63,
                                      0x52,0x66,0x55,0x6a,0x58,0x6e,0x32,0x72 };
```

Проверено: длина файла минус 12 кратна 16 — формат подтверждается. Но тег GCM
не сходится **даже на текущих бинарниках** этого репозитория, и сам ключ
не находится в `Client/system/Game.exe`. Значит файлы `.bin` в репозитории и в
`debug_files/` сделаны другой сборкой инструмента, с другим ключом.

Перебором всех 16-байтовых окон в `Game.exe` 1.38 (3,3 млн вариантов, проверка
по тегу GCM) подходящая пара ключ+IV не нашлась.

**Что это значит для локализации:** китайские названия предметов, монстров и навыков
лежат как раз в этих таблицах, а не в `StringSet`. Поэтому локализация интерфейса
(окна, кнопки, подсказки) переносится, а локализация игровых сущностей (имена
предметов из инвентаря, имена мобов, названия умений) — нет.

**Чтобы решить:** нужен либо `Game.exe`/`kop.exe` именно той сборки, которой
сделаны `.bin` (искать ключ в нём), либо сам инструмент сборки таблиц. Либо
искать ключ в других бинарниках того же клиента, если они есть.

Отдельно: даже имея `.bin` в открытом виде, это **бинарные дампы структур**
`CRawDataInfo`, а не текст. Их нужно парсить в соответствие с объявлением структуры
(`CItemInfo`, `CCharacterInfo` и т.д. в `sources/Libraries/common/include/`),
а не просто прочитать как строки.

## 7. Отложенная проверка: таблица опыта на 150 уровней

Правки внесены и статические проверки пройдены, но в игре не проверено.
Обычным набиванием не проверить — нужны сотни уровней, поэтому границы
подобраны так, чтобы их можно было выставить напрямую.

### Что сделано

`character_lvup.txt` пересобран по варианту А: 150 уровней, итог
39 999 999 973, один геометрический коэффициент +7.76 % на уровень
начиная с 60-го. Синхронизированы `DEXP[1..150]` в `variable.lua`,
`GetExp` в `functions.lua` переведён на `DEXP` (прежняя копия
обрывалась на 100-м уровне и давала `nil` выше). Убран перевод на
`int` в прогресс-баре клиента.

### Границы, где раньше всё ломалось

| Уровень | Что проверяем |
|---|---|
| 80 | старая стена: `AddExp` делил опыт на 50 начиная с 80-го |
| 111 | накопленный опыт переваливает `INT_MAX` (2 147 483 647) |
| 121 | накопленный опыт переваливает `UINT_MAX` (4 294 967 295) |
| 147 | прогресс-бар: стоимость уровня перестаёт влезать в `int` |

### Как проверять

Уровень выставляется напрямую в базе, `Server.Level.Limit = 150`:

```sql
UPDATE character SET exp = <значение> WHERE atorNome = '<ник>';
```

Опорные значения накопленного опыта из новой таблицы:

| Уровень | Накоплено |
|---|---|
| 80 | 200 232 314 |
| 111 | 2 156 508 347 |
| 121 | около 4.3 млрд |
| 147 | около 30 млрд |

### Что смотреть

1. Персонаж заходит, уровень и полоса опыта совпадают с таблицей.
2. Убийство моба даёт опыт, уровень растёт, лишнего перехода через 80
   или деления на 50 нет.
3. Полоса опыта не показывает мусор на 111, 121 и 147.
4. Опыт в базе пишется без обрезки до 32 бит.

### Известная ловушка, не связанная с таблицей

`Init_Attr.lua` ограничивает `ATTR_CEXP`, `ATTR_NLEXP`, `ATTR_CLEXP`
значением `4 200 000 000`. После перехода на 64 бита эта проверка
мёртвая — `SetAttr64` её не делает, а `GetAttrMaxVal` читают только
для шести базовых статов. Но числа в конфиге стоит поправить, чтобы
не смущали: при 4.2 млрд потолок пришёлся бы примерно на 121 уровень.

## 8. Время в логе банка гильдии: зашитое смещение GMT-5

Отложено как некритичное: гильдовский лог смотрит редко, на игру
не влияет. Правка готова и сверена, но применять, пока не «стрельнет
в колено», смысла нет.

### Что там

`sources/Client/src/UIGuildMgr.cpp:342`:

```cpp
time_t serverTime = curlog->time - 5*60*60; //GMT -5
tm *k = gmtime(&serverTime);
strftime(buf2, 200, "[%d/%m/%y] %H:%M ", k);
```

Время события переводится в зону UTC−5 вычитанием пяти часов, потом
печатается через `gmtime`, то есть фактически как UTC. Автор исходил из
того, что сервер стоит в поясе UTC−5.

### Насколько это заметно

`curlog->time` — обычное время события в секундах с 1970 года, поэтому
правильный вывод на машине с UTC+4 — это `localtime(curlog->time)` без
всякого вычитания.

Расхождение на сервере с UTC+4: минус 5 (зашито) и минус 4 (разница
поясов) — итого **на 9 часов назад**.

### Как проверить

В игре: сделать операцию с банком гильдии и сравнить время операции с
тем, что появилось в логе. Положили в банк в 14:00 — в логе будет 05:00.

В базе точнее:

```sql
SELECT guild_id, banklog FROM guild WHERE guild_id = <id гильдии>;
```

`banklog` хранит записи пятью полями через дефис
(`тип-время-сумма-количество-id`), второе поле — время в секундах с
1970 года. Отнять 18000 и перевести в UTC — получится ровно то, что
показывает клиент.

### Готовая правка

```cpp
time_t serverTime = curlog->time;
tm *k = localtime(&serverTime);
```

Почему не сделано сразу: пишущего кода `banklog` в исходниках GroupServer
найти не удалось — есть только читатель (`GameDB.cpp:4626`) и
`update guild set banklog` (`GameDB.cpp:4676`). Пока не проверено, что
там кладётся обычный `time(0)`, менять вывод исторических записей
рискованно.
